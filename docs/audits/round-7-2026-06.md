onboarding becomes a conversation, the product builds itself around the user),
plus a performance comparison and a smoke-test checklist. Verdicts: kept /

## Deferred, and why

These are honest deferrals: removing them would either break live behavior or
require a data-model migration, both of which conflict with the round's
zero-functional-change cleanup contract.

- **Abstract template value set is load-bearing.** The abstract templates
  (`personal`, `investor`, `business`, `family_office`, `custom` in
  `lib/data/workspace-templates.ts`) are no longer what drives onboarding (the
  real-life set in `lib/onboarding/templates.ts` does that now), but the
  `template_key` *values* are still wired into live, non-onboarding code:
  work-space creation (`app/dashboard/work/spaces/new`), space theming
  (space-theme), thing labels (things-label), suggested questions, mode
  actions, and the `organizations.template_key` CHECK constraint. Deleting the
  set would change work-space-creation behavior and force a migration that
  rewrites the CHECK constraint and existing rows. Deferred to a dedicated
  refactor. The round-7 objective (abstract templates no longer shape
  onboarding) is met regardless.
- **`onboarding_sessions` table is now orphaned.** It was written only by the
  deleted chat flow. Left in place; it carries no runtime cost and dropping it
  needs a migration. Deferred.

## Performance verification vs baseline

Per `docs/perf/2026-06-baseline.md`, the dashboard rows carry `_measure_`
placeholders (Lighthouse needs an authenticated production run, not available
from the build environment), so verification here is static:

- The entire onboarding flow (`/onboarding/*`) is pre-dashboard and runs only
  once per user; it is not on the recurring dashboard render path.
- The only change to a hot path is the dashboard layout adding `shouldShowReveal`
  to its existing `Promise.all`. It runs in parallel with the other reads and
  adds no serial await, so dashboard TTFB is unchanged.
- The reveal overlay is a client component gated behind a one-time flag; once
  `onboarding_completed_at` is set it never renders again.

No page touched this round moved a number the wrong way against the baseline.

## Smoke-test checklist

1. New user signs up, lands on `/onboarding/demo`; slides auto-advance and skip
   works, leading into `/onboarding/conversation`.
2. Conversation runs, progress reads "Question N of M", a single question can be
   skipped, synthesis produces a plan, `/onboarding/preview` is editable.
3. "Build my Oria" executes, routes to `/onboarding/link`; Gmail connect is
   live, others read as coming soon; skip/done reaches the dashboard.
4. Dashboard shows the reveal overlay once; after dismissal it never returns
   (reload to confirm).
5. Existing users never see the reveal and never get bounced into onboarding.
6. Reshape reachable from the command palette ("Reshape Oria"), the feature
   index, Settings -> Preferences, and the user menu ("Reshape my Oria");
   produces an additive plan with a preview and a 24h undo.
7. The reprompt banner's "Start" now opens `/onboarding/demo`.
8. Locale switch (ar/fr/es) shows translated onboarding and reshape copy with no
   missing-key fallbacks.
