## Soft-delete: additive-only assumptions audited

The reshape engine was additive-only before this round; DELETE makes
`organizations` and `custom_sections` soft-deletable (`deleted_at`). Every read
that surfaces these to a user must now exclude soft-deleted rows. Audit result:

| Read path | Filters `deleted_at`? | Action |
|---|---|---|
| `getCurrentContext` (active org) | yes | F1 (also the API-layer write block, see below) |
| `listUserSpaces` (space switcher) | yes | F1 |
| `listAllSections` (custom_sections) | yes | **F5 fix** (was leaking) |
| `listCustomSections` | yes | **F5 fix** (was leaking) |
| `getCustomSectionById` | yes | **F5 fix** (was leaking) |
| `countCustomSectionUploads` (uploads) | yes | pre-existing |

The three F5 fixes close a latent gap. Note on schema reality: migration 0010
("soft delete") added `deleted_at` only to `uploads`, NOT to `custom_sections`
or `organizations` (a wrong assumption during the round that the remote schema
check at deploy time caught). Migration 0064 therefore adds `deleted_at` to both
`organizations` and `custom_sections`; nothing soft-deleted sections before this
round, so no read filtered the (previously non-existent) column. The reshape
DELETE patch now sets it, so those reads needed the filter. The regression test
(`tests/unit/section-scoping.test.ts`) now also exercises the `deleted_at` filter.

### Blocking new data into a soft-deleted space (API layer)

`getCurrentContext` filters `deleted_at IS NULL` on the active org. A soft-deleted
space therefore never resolves into a request context, so `requireContext` (the
gate every write goes through) cannot return it. New uploads, items, sections,
and reminders all derive their `organization_id` from that context, so none can
land in a soft-deleted space. No per-endpoint guard is needed.

### 24-hour purge

`purgeExpiredSoftDeletes` runs from the existing hourly cron
(`/api/cron/send-reminders`, Round 8 infrastructure). It hard-deletes any
`organizations`/`custom_sections` row whose `deleted_at` is older than 24 hours,
children cascading via existing FKs, and audits each removal as
`setup_change_purged`. Within the 24h window, undo simply clears `deleted_at`.

## Shared classifier base extracted

`classifyReasoningIntent` (Round 11) and `classifySetupIntent` (Round 12) shared
the same scaffold: fetch the user's conversation provider, run a fast-tier
JSON-mode completion, strip any code fence, parse, never throw. Consolidated into
`lib/ai/classifiers/base.ts` (`runFastJsonClassifier`). Each classifier now holds
only its prompt + parse mapping. Two call sites, genuinely duplicated logic, so
consolidation is warranted (vs. the standing rule's "single-use helper: leave it").

## Performance

Baseline: `docs/perf/2026-06-baseline.md`. No render-path regressions.

- **Classifier overhead (<200ms target).** Both Ask classifiers run inside the
  same `Promise.all` as retrieval (`app/api/ask/route.ts`), never sequentially on
  the answer path. The setup-intent classifier adds zero wall-clock when retrieval
  is the slower leg (it usually is). Both are fast-tier, ~40-60 output tokens.
- **Image payload (<50MB for 5 images target).** Server validation caps each image
  at 10MB decoded and 5 images per query, so the decoded payload is <=50MB by
  construction. Base64 inflates the request body ~1.37x over the wire; this is a
  user-initiated multimodal request, bounded and off the main data fetch. HEIC is
  converted to JPEG server-side (`heic-convert`, dynamic import, kept out of cold
  starts that do not need it).
- **Soft-delete filters** ride partial indexes (`... WHERE deleted_at IS NOT NULL`,
  migration 0064), so the common `deleted_at IS NULL` reads stay on the existing
  org/section indexes.

## Known limitations / deferred

- **Gemini vision.** The Gemini provider adapter joins text parts and drops
  inline images (documented in `lib/ai-providers/gemini.ts`). A user whose
  connected conversation provider is Gemini will have attached images silently
  ignored; Anthropic (Oria's default) and OpenAI both read them. Reaching Gemini
  vision parity is out of scope for this round.
- **Setup-intent on image queries.** When images are attached, setup-intent
  detection is skipped (an image query is a vision question, never a structural
  change), so an image is never lost to a reshape reroute.

## Migration

`0064_org_soft_delete.sql` adds `deleted_at` to **both** `organizations` and
`custom_sections` (migration 0010 only covered `uploads`), plus a partial index on
each. Idempotent (`IF NOT EXISTS`) and additive. Applied to production via
`npx supabase db push` before the deploy; verified both columns exist remotely.
