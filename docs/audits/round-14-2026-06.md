A breadth round: make every screen feel intentional, clear, and fast. Six
feature areas plus this cleanup. This document records what shipped, the
judgement calls, the section-by-section review, and what was deliberately
deferred (with reasons) so the user can validate the "apply this thinking
everywhere" intent.

## F1 - Settings

- **Tab reorder** (`app/dashboard/settings/page.tsx` TABS): now General, Connections, AI, Appearance, Preferences, Sections, Circles, Workspaces, Storage, Security, Privacy. Honors the architectural decision: Connections up (2nd), Storage down (9th). The structural tabs (Sections/Circles/Workspaces) are kept as real features rather than dropped.
- **Control descriptions**: the only label-only controls were the Preferences "Response length" and "Tone" segmented choices; both gained one-line purpose descriptions (`settings_help.response_length` / `.tone`), localized in 4 languages. The "Timeline" and "Pinned metrics"/"Focus areas" controls already had descriptions (verified).
- **Reshape prominence**: a primary Reshape card on the Settings landing (General tab), a Reshape entry in the sidebar system cluster, and broadened command-palette keywords (`make/add/delete/remove/rename/...`).
- **Per-space appearance**: already implemented before this round. the Appearance tab writes `accent_color` + `shadow_color` to the active org only ("Changes apply to this space only"). Verified and kept; no migration needed.

**Judgement call / deferral:** per-org *theme variant* (light/dark) override was deferred. Theme is a client-side global toggle; making it per-org is a larger change and per-org accent already delivers the per-space identity. Documented so the user can decide if per-org light/dark is wanted later. Because of this and because per-org accent already exists, **migration 0066 was not needed** this round.

## F3 - naming

**Renamed (user-facing, localized 4 langs):**
- "Inbox" -> "Uploads": sidebar labels (personal + work nav), the uploads page title/topbar, empty-state copy (`empty.inbox_headline`/`inbox_desc`).
- "Things" -> "Items": the label resolver default (`resolveThingsLabel`), the page title, the sidebar fallback labels, the command-palette group heading (`group_things`), and the feature-index entry (`features.things.title`). The investor "Assets" label is preserved. Chosen name **"Items"** (the spec's recommendation) over "Records"/"Library": it is the clearest, most standard UX term for a mixed set of people/vehicles/properties.

**Reviewed but kept (with reasoning):**
- "Unsorted inbox" (the review section, `/dashboard/sections/review`): a *different* concept from uploads (items Oria could not auto-file). Kept; renaming to Uploads would conflate two ideas.
- Gmail/email "inbox" references (scan copy, verify-email copy): refer to the user's actual email inbox. Kept.
- Internal route paths `/dashboard/inbox` and `/dashboard/things`, the `things_label` column, `InboxIcon`/`InboxList`/`ThingsRename` identifiers: kept to avoid link/import breakage. user-facing labels are what changed.
- "Bills", "Health", "Travel", "Calendar", "Trackables", "Reshape", "Connections", "Storage": clear and accurate, kept.

**Diet -> Health merge:** Diet folded into Health as a sub-area. The standalone Diet nav entry was removed; Health gained a "Diet" tab; the personal template no longer seeds a separate Diet section. **Schema reality (verified):** diet entries are `memory_items` with `smart_section='diet'` (a smart aggregation), not rows in a separate Diet section table, so there was nothing to move and **no destructive migration was required**. existing diet data is intact and now reached via Health > Diet. The dedicated diet meal-tracker page (`/dashboard/diet`) is kept and linked from the Health tab rather than rebuilt inline (lower risk; preserves the macro/week tracker).

## F5 - calendar + density

- **Calendar (named bug fixed):** diet meals were `memory_items` with `occurred_at`, so a logged pasta entry appeared as a calendar event. `loadCalendar` now excludes `smart_section='diet'` (`lib/data/calendar.ts`), keeping every other dated item including the common null-smart_section rows. Verified: a diet entry no longer surfaces on the calendar.
- The calendar already has a rich filter UI (kind / category / topic pills in `components/calendar/calendar-view.tsx`), so the "let the user toggle what shows" requirement was already met.

**Layout density - reviewed:**
- Section header info strip (`[section]/page.tsx` Layout): already a flex row with the item count pushed right via `ml-auto`, not a wasteful full-width strip. No change needed.
- Stale copy removed: the "Microsoft (Outlook, OneDrive, Office) is coming soon" note in the Google services panel was wrong (Microsoft is live below it); removed, and the dead `microsoft_soon` key dropped from all four locales.

**Deferred (documented honestly):**
- **Bills declutter** and a broad cross-product density rewrite. The Bills page stacks ~9 blocks; a redesign reserving right-side space for financial visuals is real design work that, done without a live visual environment, risks regressions. Deferred rather than done blind, per "polish should never break things."
- **Stricter calendar sourcing** (showing *only* connector events + reminders + bills, and wiring `calendar_events` into `loadCalendar`): the connector-events table is not currently merged into the calendar view, and stripping all dated documents (flights, hotel check-ins) could remove content users value. The named diet bug is fixed; the stricter rebuild is deferred.

## F2 - connections hub redesign (DEFERRED)

Not shipped this round. The single-page two-zone hub (Connected group-by-account on top, a no-scroll Available grid below, unified status dots) is a multi-component rebuild touching `connections-panel`, `cloud-services-panel`, `microsoft-services-panel`, the per-service row components, and the onboarding link grid. Doing it well needs the live visual environment to verify the no-scroll-on-1280x800 layout and the account-grouping cards. Attempting it blind risked breaking working connection flows, so it was deferred rather than half-built. The one safe, concrete connections fix (stale "coming soon" copy) was made. Recommended as the first item of a follow-up round; the recon map for it is in this round's notes (duplicated status-dot maps in 3 files, duplicated account-grouping in 2 files, and `lib/cloud/shared/format.ts:syncedLabel` are the consolidation seams).

## Performance

- `npm run build` passes (Turbopack). 22 runtime dependencies; no heavy dependency was added this round (the round was rename/reorder/filter work, almost no new client JS). The build-time route table renders but Turbopack's output does not print per-route First Load JS in this environment.
- **Lighthouse**: not run. the dashboard is auth-gated and this environment has no browser/Chromium (same constraint documented in `docs/perf/2026-06-baseline.md`). A signed-in maintainer Lighthouse pass is the open item. The calendar change is a net query *reduction* (one extra `OR` predicate, fewer rows returned), so it cannot regress calendar load.
- No N+1 introduced; the calendar filter is a single added predicate on an existing query.

## Gates

`npm run build`, `npm test` (200 passing), `npm run lint` (0 errors; 2 pre-existing warnings) green at every commit. 4-language key parity verified after each copy change. No U+2014 introduced (verified across the round range).
